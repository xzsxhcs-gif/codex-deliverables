## 上游实际技术路线

1. Python 总谱通过明确音符、和弦、配器、力度、表情控制器和速度图描述音乐。`notes.json` 提供每个音符的通道、音高、力度、起止秒数、标签，以及拍／小节边界。
2. `render.c` 使用 TinySoundFont 读取 GeneralUser GS，按通道合成48kHz立体声浮点分轨；`mix_kit.py` 执行声像、滤波、混响、母线动态与峰值保护，输出 WAV。
3. 原作另把同一音乐数据写入 `vis5.json`；画面按 `renderAt(t)` 确定性绘制。平面工作区用 Canvas，世界与后期用 WebGL。
4. Playwright 以明确的 `t = frame / fps` 驱动 Chrome；截图管道送给 FFmpeg，再合入固定音频。原文提到300帧一段、可恢复渲染，以及场景代码变更后避开旧缓存。
5. 原作通过可追踪的形变把旋律变成山脊、和声变成水、短音变成星，再回到原来的音乐结构；导演原则是“意图—动作—可见且可听的结果”。

原始上游 MIDI 导出有已知问题：文件头长度字段、控制器、初始留白和速度积分等。上一音乐任务已经在独立工作副本修复并验证。本片优先沿用已验证的 `where-light-returns` 音乐与数据，不能退回上游旧导出覆盖它们。

## 与本片有关的故障根因及规避

### 时间与音符

- 所有轨道必须共享横向时间变换；音符横坐标是开始时间，宽度是持续时间，纵坐标在各轨内统一映射音高。
- 和弦中的同时音起点应对齐；合法重叠与复调需要保留。不得为了画面整齐改写音乐。
- 不用90 BPM硬编码计算全部画面时点；现有曲子末尾会渐慢。直接用 JSON 中的秒数及拍／小节边界。
- 音符激活应在真实开始时间之后第一个输出帧出现，30 FPS 的量化误差小于一帧33.34ms。镜头和助手可预备动作，但发光的演奏状态不可提前。
- 自动化曲线若出现，应单独分层，避免被看成音符；本片不必复制参考原作的代码卡、聊天界面或大量解释字幕。

### 三维摄像机与回归

- 原作回程曾直接使用河道切线作为朝向，导致角度停滞再急旋；最后采用独立世界空间回程、平稳转向、零滚转和约2.1秒交接。
- 对路径关键帧可用保形三次插值 PCHIP，再做平滑；避免各属性分别突然切换规则，尤其不要在某个高度阈值突然改变放置公式。
- 本片应在二维与三维之间保留共同匹配的几何对象，保持屏幕位置、尺度、切线方向连续；一个画面中几何渐变，不靠大量粒子遮住跳切。

### 水面与时间混叠

- 原作把水放在约160,000单位巨大的两三角形平面上，再插值变化量，产生精度误差与左右抖动。最终改为逐像素由相机射线求水面交点与准确深度。
- 反射扰动曾大到130像素；修正至低幅度约0.012，并模糊、降低镜像线强度至约35%。不能用夸张噪声扭曲水面。
- 另一次抖动来自水纹约13单位，而相机每帧前进约7.6单位。解决方法是加大间距、靠近镜头淡出高频纹理、删除密集排线；不应只增加后期模糊掩盖根因。
- 对本片更可靠的实现是世界坐标锚定的低频水面与受控细节，按像素／距离衰减高频。摄像机运动和波纹运动都使用连续绝对时间公式。

### 渲染与交付

- 原作无GPU的云渲染需要数小时，不能直接承诺本环境实时运行。应尽早测试实际渲染器及固定分辨率帧成本，再决定细节密度。
- 低清预览之后仍需在1080p检查水面、细线、字体、泛光与运动，不仅看静帧。软件GPU与实机GPU可能暴露不同时间混叠。
- 输出需包含确定性源工程与运行说明；渲染缓存应含分辨率、帧率、场景源码和音乐数据指纹，避免误用旧帧。
